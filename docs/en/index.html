MitiruEngine

Header-only C++20 game engine

Gameplay in C++. UI in CEF (HTML/CSS). Bridged by a thin signal-only layer.

Get Started → View on GitHub

MitiruEngine is a header-only C++20 game engine designed around a simple split: gameplay runs in C++, UI runs in HTML/CSS through CEF, and the two communicate over a deliberately thin signal-only bridge. You write scenes, state machines, novel VMs, AI, and physics in C++ where the debugger and the profiler can see them. You build the HUD, menus, dialogs, and transitions in HTML/CSS where designers and the web ecosystem are at home.

The engine ships as 33 modules across 583 headers. You consume it through CMake FetchContent and link a single INTERFACE target — there is no precompiled library to track per platform. The hello_headless example runs on CI without a GPU; full graphics scenes use a shared IDevice abstraction over DX11, DX12, Vulkan, OpenGL, WebGL, and a Null backend that the test suite falls back to automatically.

The point of the C++/CEF split is not novelty. It is to keep gameplay state in one place. JavaScript reports user input to C++ (pointerdown on this button, dropEnd at this slot). C++ reports the canonical view back to JavaScript (hp=80, show dialog "..."). The bridge stays small enough to audit by hand. Save data lives in versioned nlohmann::json, validated at load through bundled JSON Schema and migrated forward through dedicated helpers — post-launch save compatibility is a structural property, not a hope.

Performance and correctness are verified continuously. Tracy zones are baked into the hot paths so frame-level CPU and GPU timelines are one keystroke away. The test suite holds 2254 Catch2 unit and integration tests green, with Playwright and Chrome DevTools MCP driving real-browser verification on top.

If you build games where the UI surface is large and the gameplay surface is real, MitiruEngine wants to be the layer underneath.

Three Pillars

01

C++ for gameplay

Scenes, state machines, novel VMs, physics, AI — every moving part is C++. Deterministic, profilable, friendly to both debuggers and LLMs.

02

CEF for UI

Build HUD, menus, dialogs, transitions in HTML/CSS. Lean on the web ecosystem without dragging it into gameplay.

03

Signal-only bridge

JS to C++ reports events; C++ to JS describes the view. Keep the bridge thin so gameplay state stays in one place.

Features

Header-only architecture

33 modules, 583 headers. Pull in via CMake FetchContent and link a single INTERFACE target — no precompiled library to ship.

Multi-backend graphics

DX11, DX12, Vulkan, OpenGL, WebGL, Null — all behind the same IDevice interface. CI falls back to Null automatically.

Tracy profiling

Tracy integration baked in. Frame-level hotspots and GPU timeline capture with minimal setup.

Save schema with migration

Versioned JSON save format with migration helpers — keep post-launch save compatibility a structural property, not a hope.

JSON Schema validation

Novel scripts, i18n tables, balance data, art bible — all content data is validated against JSON Schema at load time.

Test-first culture

2254 Catch2 unit and integration tests green. Playwright and Chrome DevTools MCP automate real-browser verification.

Example

A minimal consumer

Pull MitiruEngine in via FetchContent and link Mitiru::mitiru. The header-only engine is ready to go. Start from hello_headless — it runs on CI without a GPU.

Browse all 11 examples → 

// examples/hello_headless/main.cpp
#include <mitiru/Mitiru.hpp>
#include <cstdio>

int main() {
    std::printf("MitiruEngine hello_headless — OK\n");
    return 0;
}
# CMakeLists.txt (consumer game)
include(FetchContent)
FetchContent_Declare(Mitiru
    GIT_REPOSITORY https://github.com/mogmog-0110/MitiruEngine.git
    GIT_TAG        main)
FetchContent_MakeAvailable(Mitiru)

add_executable(MyGame src/main.cpp)
target_link_libraries(MyGame PRIVATE Mitiru::mitiru)
