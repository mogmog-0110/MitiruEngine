この教本の使い方

手順やること
① 写経するコードはコピペしない。手で打つ。MITIRU_GAME や flat POD の書き方は、打った回数だけ体に入る
② 読み方を読むコードの下に「読み方」がある。1 行ずつ分からなくていい。ブロックごとに何をしているかだけ掴む
③ 動かす各章の最後に必ず「動いて見えるもの」がある。動かない状態で次の章へ進まない
④ 1 か所変える・1 問答える改造課題と質問がある。質問は「答え」を開いて読むだけでいい

各手順は 操作（どこで何を打つか）→ なぜ（何のためにやるか）→ 確認（うまくいったかの見分け方）の順に並んでいる。確認が合わなかったら、その手順で止まって見直す。

知らない言葉が出たら、その場の説明か、巻末の用語集、あるいは docs/GLOSSARY.md を見る。

前提: この教本は docs/GETTING_STARTED.md の手順で mitiru CLI が使える状態から始める。CLI が無ければ先にそちらを終わらせる。

01

プロジェクトを作る

この章のゴールmitiru run で 1280×720 のウィンドウが開き、何かが画面に出る状態にする。

1mitiru new でプロジェクトを作る

プロジェクト

ゲーム 1 本ぶんのフォルダ。mitiru.toml（設定）と src/main.cpp（コード）が入っている。

操作
  1. ターミナルで、プロジェクトを置きたい場所に cd
  2. mitiru new my_game と打つ
  3. cd my_game
なぜ

mitiru new は CMake の設定やアセット置き場を含む雛形を一式作る。空フォルダから手で組むより確実。

確認

my_game フォルダの中に mitiru.toml と src/main.cpp がある。

2ビルドして動かす

ビルド

書いた C++ をゲーム用の DLL に変換すること。しないと src/main.cpp の変更は反映されない。

host と Game DLLdocs/GLOSSARY.md

mitiru_host.exe（host）が、あなたのゲームの DLL を読み込んで毎フレーム動かす。ゲームのコードは host の内部に直接触らない。

なぜ

mitiru run は「ビルド」と「実行」を 1 コマンドにまとめたもの。初回だけエンジン本体のコンパイルが走るため 5〜10 分かかるが、2 回目以降は数秒〜数十秒で終わる。

操作
  1. mitiru run と打つ
  2. 初回は待つ（進捗が流れる）
確認

1280×720 のウィンドウが開き、跳ねるボールや図形が動いて見える（welcome テンプレートの既定画面）。Esc で終了する。

動かないとき: mitiru doctor を打つと、前提ツールの有無と「よくある症状 → 対処」の表が出る。DLL not found や窓が出ないは、まずここを見る。
改造課題・1分

mitiru.toml の [window] の width / height を変えて、ウィンドウの大きさを変える。

ヒント

数値を書き換えて保存したら、もう一度 mitiru run。

質問

mitiru run を 2 回目に打つと、なぜ 1 回目より速く終わると思うか。予想でよい。

答え

2 回目はソースが変わっていない部分を作り直さないから。ビルドは ninja という道具が「前回から変わったファイルだけ」を見て、変わっていないものは前回のコンパイル結果をそのまま使う。1 回目はエンジン本体を含め全部が「初めて」なので全部作る。

02

動く四角

この章のゴール矢印キー（または WASD）で青い四角が画面の中を動く。

src/main.cpp の中身を、この章のものに丸ごと置き換える。

1状態を 1 個の struct に置く

GameMemorydocs/GLOSSARY.md

ゲームの全状態を入れる 1 個の struct。MITIRU_GAME(T) の T がこれにあたる。

なぜ

MitiruEngine は状態をクラスの階層やヒープに散らばせず、1 個の flat な struct にまとめる設計 (flat POD)。std::vector や std::string は使わず、素の数値だけを持つ。

操作

src/main.cpp の中身を、次のコードで置き換える（1 行ずつ手で打つ）。

src/main.cppまずここまで
#include <mitiru.hpp>
using namespace mitiru;

struct MyGame
{
    float x = 640.0f, y = 360.0f;   // 四角の位置

    void update(Input in, Hud hud, float dt)
    {
        constexpr float kSpeed = 320.0f;
        Stick dir = in.move();      // 矢印/WASD/パッドをまとめて -1..1 で返す
        x += dir.x * kSpeed * dt;
        y += dir.y * kSpeed * dt;
    }

    void draw(Screen& s)
    {
        s.fillScreen(hex(0x101018));
        s.drawRectCentered(x, y, 40.0f, 40.0f, hex(0x4C95F2));
    }
};

MITIRU_GAME(MyGame)

読み方

struct MyGame
ゲームの状態。ここでは位置 x, y だけ
update(Input, Hud, float dt)
毎フレーム 1 回呼ばれる。dt は前フレームからの経過秒。「1 秒あたり kSpeed 進む」を dt 倍することで、フレームレートが変わっても速さが変わらない
in.move()
矢印キー・WASD・パッドのスティックをまとめて -1..1 の Stick{x, y} で返す。デバイスごとに分岐を書かなくてよい
draw(Screen&)
毎フレーム 1 回呼ばれる。ここでは状態を変えず、見た目を並べるだけ
MITIRU_GAME(MyGame)
この 1 行で DLL の入口ができる。MyGame が flat POD (trivially copyable) でなければコンパイルエラーになる
確認

mitiru run を打つと、暗い画面に青い四角が出て、矢印キーで動く。

2画面の外に出さないようにする

なぜ

今のままだと四角は画面の外まで走り続ける。docs/CPP_GAMEPLAY_GUIDE.md にある通り、値を範囲に収めるのはよくある処理。ここでは std::clamp のように自分で min/max を書く。

操作

update の最後（y += ... の次）に、次の 2 行を足す。

src/main.cppupdate の中、末尾に追加
        if (x < 20.0f) x = 20.0f; if (x > 1260.0f) x = 1260.0f;
        if (y < 20.0f) y = 20.0f; if (y > 700.0f) y = 700.0f;
確認

四角が画面の端で止まり、外へは出ない。

改造課題・5分

四角の色を、Space を押している間だけ赤に変える。押している間の判定は in.down(Key::Space)。

ヒント

draw の中で色を決める変数を 1 個作り、update ではなく draw の中で in.down(...) を見てもよいし、update で bool を state に持って draw から読んでもよい。draw は Input を受け取らないので、状態として持つ方が本筋。

質問

kSpeed を dt と掛けずに x += dir.x * kSpeed;（dt 無し）にすると、何が起きると思うか。

答え

実行環境のフレームレートによって速さが変わる。60fps なら 1 秒間に 60 回 kSpeed だけ進むが、120fps なら 120 回進むので 2 倍速く見える。dt（前フレームからの経過秒）を掛けると「1 秒あたり kSpeed」になり、フレームレートに依存しなくなる。

03

リングを取る

この章のゴール画面に浮かぶ5 個のリングに四角が触れると消え、取った数が左上に出る。

1リングを複数持つ

配列flat POD の中の複数個

std::vector は使えないが、個数が最初から決まっているなら普通の C 配列 Ring rings[5] で十分 flat POD になる。個数が可変なら FixedVec<T,N>（docs/FLAT_POD.md）を使う。

なぜ

リングも「ゲームの状態」の一部なので、MyGame の中に置く。ここに置いておけば、後で rewind ring や録画再生の対象にそのまま乗る。

操作

第2章のコードに、struct MyGame の外側（上）に Ring を追加し、MyGame の中にリングの配列とスコアを足す。

src/main.cpp#include の下、struct MyGame の前に追加
struct Ring { float x, y; bool taken; std::uint8_t _pad[3]; };  // _pad: 暗黙の詰め物を残さない
src/main.cppstruct MyGame の中、x, y の下に追加
    int score = 0;

    Ring rings[5] = {
        {300.0f, 200.0f, false},
        {980.0f, 200.0f, false},
        {640.0f, 120.0f, false},
        {300.0f, 560.0f, false},
        {980.0f, 560.0f, false},
    };
確認

mitiru run はまだ見た目が変わらない（リングを描いていないので）。エラーが出ずにビルドが通ることだけ確認する。

2触れたら消える判定を書く

距離での判定

四角とリングの中心の距離が半径より近ければ「触れた」とみなす簡単な当たり判定。dx*dx + dy*dy は距離の 2 乗（sqrt を避けて軽くする定石）。

なぜ

厳密な四角と円の当たり判定より簡単で、写経の題材としては十分。本格的な当たり判定が要る場合は Collide2D.hpp（moveAndCollide）がある。

操作

update の中、画面端の clamp の後ろに追加する。

src/main.cppupdate の中、末尾に追加
        for (auto& r : rings)
        {
            if (r.taken) { continue; }
            const float dx = x - r.x, dy = y - r.y;
            if (dx * dx + dy * dy < 32.0f * 32.0f)
            {
                r.taken = true;
                ++score;
                hud.play("pop");
            }
        }

読み方

for (auto& r : rings)
5 個のリングを 1 個ずつ見る。& が付いているので r.taken = true が本体に反映される
hud.play("pop")
効果音を鳴らす。assets/audio/ に用意された音を id で鳴らす、host への「お願い」(intent)
確認

まだ見えないが、ビルドは通る。

3リングとスコアを描く

なぜ

update は状態を変えるだけ、draw は今の状態を見て絵にするだけ、という役割分担を保つ。

操作

draw の中身を次の形に置き換える。

src/main.cppdraw を置き換え
    void draw(Screen& s)
    {
        s.fillScreen(hex(0x101018));

        for (const auto& r : rings)
        {
            if (r.taken) { continue; }
            s.drawCircleFrame({r.x, r.y}, 20.0f, hex(0xF5C842), 4.0f);
        }

        s.drawRectCentered(x, y, 40.0f, 40.0f, hex(0x4C95F2));

        char buf[32];
        std::snprintf(buf, sizeof(buf), "Rings: %d / 5", score);
        s.drawTextInRect({20.0f, 20.0f, 300.0f, 40.0f}, buf, color::White, 24.0f);
    }
忘れやすい: std::snprintf を使うので、ファイル先頭の #include <mitiru.hpp> の下に #include <cstdio> を足す。
確認

金色の輪が 5 個浮かび、四角で触れると消えて「Rings: 1 / 5」のように左上の数字が増える。assets/audio/pop.wav の音も鳴る。

改造課題・5分

5 個全部取ったら「CLEAR!」を画面中央に出す。score == 5 を draw で見て、drawTextInRect をもう 1 回呼ぶ。

ヒント

中央あたりの矩形は {440.0f, 320.0f, 400.0f, 80.0f} くらい。文字サイズは大きめ (48.0f) にすると見栄えがする。

質問

リングの当たり判定を update ではなく draw に書くと、何が問題になると思うか。

答え

draw は「今の状態を絵にするだけ」の場所で、状態を変えてはいけない、という役割分担が壊れる。MitiruEngine は「状態を変えるのは update だけ」という前提で、rewind（巻き戻し）や録画再生を組んでいる。draw で taken を書き換えると、巻き戻し中に draw が呼ばれるたびに状態が変わってしまい、同じフレームを何度描いても結果が変わる、という壊れ方をする。

04

敵を出して当たり判定

この章のゴール敵に触れるとHP が減る。わざと壊した状態を作って、エンジンが自分でおかしさに気づくところを見る。

第3章のコードに、HP と複数の敵を足す。

1個数が変わりうる配列は FixedVec

FixedVec<T,N>docs/FLAT_POD.md

上限 N が決まった、ポインタを持たない配列。push_back / size() など std::vector に近い手触りだが、内部はただの T[N] なので flat POD のまま。

なぜ

第3章の Ring rings[5] は個数が最初から確定していたので生配列で十分だった。敵は後で増やしたり全滅させたりしたくなるので、上限だけ決めて FixedVec を使う。

操作

struct MyGame の外側、Ring の下に敵の struct と初期配置を作る関数を足す。

src/main.cpp#include の下、Ring の下に追加
#include <mitiru/module/Invariant.hpp>   // MITIRU_INVARIANT
#include <mitiru/core/FixedVec.hpp>      // 個数の変わる配列

struct Enemy
{
    float x = 0.0f, y = 0.0f;         // 今の位置 (draw と当たり判定はこれを見る)
    float baseX = 0.0f, baseY = 0.0f;
    float phase = 0.0f;
    bool  alive = true;
    std::uint8_t _pad[3] = {};   // 暗黙の詰め物を残さない (状態をバイト単位で比べるため)
};

constexpr FixedVec<Enemy, 3> makeInitialEnemies()
{
    FixedVec<Enemy, 3> v;
    Enemy touching; touching.baseX = 640.0f; touching.baseY = 360.0f; touching.phase = 0.0f;
    (void)v.push_back(touching);   // わざとプレイヤーの初期位置へ重ねる (後述)
    Enemy a; a.baseX = 300.0f; a.baseY = 500.0f; a.phase = 1.0f;
    (void)v.push_back(a);
    Enemy b; b.baseX = 980.0f; b.baseY = 220.0f; b.phase = 2.4f;
    (void)v.push_back(b);
    return v;
}

読み方

x, y / baseX, baseY, phase
今の位置と、揺れの中心・位相。update で毎フレーム x, y を baseX, baseY と時間から計算し直す
touching (1体目)
わざとプレイヤーの初期位置 (640, 360) に重ねて置く。何フレームか動かないと減らない、では警告を見るまで待たされるので、この章だけの特別な配置
push_back の戻り値
[[nodiscard]] なので (void) で明示的に無視する。上限 3 を超えて足そうとすると false が返り、黙って捨てられることはない
確認

まだビルドは通らない (MyGame 側の変更がまだ)。次の手順まで進める。

2「HP は負にならない」を宣言する

MITIRU_INVARIANTdocs/GLOSSARY.md

「この struct の状態は、いつでもこの条件を満たしているべき」という前提をコードで宣言する。破れたフレームでエンジンが自分で気づいて教えてくれる。

なぜ

「HP が負にならないよう気をつけて実装する」だけでは、いつか誰かが (未来の自分も含めて) 見落とす。宣言しておけば、見落としが起きた瞬間にエンジン側が検知する。テストを書くのと近いが、こちらは「毎フレーム自動で見張り続ける」。

操作

struct MyGame の中に hp と敵の配列、経過時間を足す。

src/main.cppstruct MyGame の中、score の下に追加
    int   hp = 100;                 // 0 未満にならない、はず
    float t = 0.0f;                 // 敵をゆらすための経過時間
    FixedVec<Enemy, 3> enemies = makeInitialEnemies();
操作

MITIRU_GAME(MyGame) の下に、この 2 行を足す (グローバル scope、struct の外)。

src/main.cppファイル末尾、MITIRU_GAME の下
MITIRU_INVARIANT(MyGame, "hp_not_negative", g.hp >= 0)
MITIRU_INVARIANTS_EXPORT()

読み方

MITIRU_INVARIANT(MyGame, 名前, 式)
g という名前で const MyGame& を受け取れる。式が false になったフレームが「違反」
MITIRU_INVARIANTS_EXPORT()
宣言した不変条件を host が読めるようにする 1 行。ファイルにつき 1 回だけ書く
確認

まだ見えないが、ビルドは通る。

3触れたら減る判定と表示

なぜ

第3章のリングと同じ距離判定を使い回す。今回は わざと clamp しない ── 重なり続けると毎フレーム減り続け、HP は一気にマイナスまで落ちる。invariant がこれを検知する様子を見るのが目的。

操作

update の末尾 (リングの判定の後ろ) に追加する。

src/main.cppupdate の中、末尾に追加
        t += dt;
        for (auto& e : enemies)
        {
            if (!e.alive) { continue; }
            e.x = e.baseX + std::sin(t * 1.5f + e.phase) * 120.0f;
            e.y = e.baseY;

            const float dx = x - e.x, dy = y - e.y;
            if (dx * dx + dy * dy < 30.0f * 30.0f)
            {
                hp -= 40;
            }
        }
操作

draw に敵を描く行と、HP を表示する行を足す (%d / 5 の後ろに続ける)。

src/main.cppdraw の中、リングを描く for の下に追加

        {

            s.drawRectCentered(e.x, e.y, 34.0f, 34.0f, hex(0xE5484D));
        }

確認

mitiru run すると、赤い四角の敵が 3 体、うち 1 体はプレイヤーに重なった状態で始まる。数フレームでターミナルに次の警告が出る:

ターミナル出力実測
[mitiru] frame 3: hp_not_negative (MITIRU_INVARIANT) が破れた
         → docs/BUG_HUNT.md の `invariant` の行を見る

左上の表示も HP: -260 のようにマイナスへ落ちていく。

おまけで見えるもの: 同じ実行で MyGame に GameMemory padding が 15 byte ある という警告も出ることがある。これは bool と次の float の間にできる詰め物 (アライメント) の指摘で、動作は壊れないが、録画・巻き戻しの bit 単位比較では気にする価値がある、という程度の注意。
改造課題・10分

「重なっている間ずっと削れる」を「1回だけ削れる」に直す。被弾後 1 秒は無敵にする invuln (残り無敵時間) を MyGame に足し、invuln > 0 なら判定をスキップして invuln -= dt、当たったら invuln = 1.0f にする。

ヒント

hp -= 40; の直前に if (invuln > 0.0f) { continue; } を、直後に invuln = 1.0f; を足す。invuln 自体は for の外、t += dt; の下あたりで if (invuln > 0.0f) { invuln -= dt; } のように毎フレーム減らす。

質問

MITIRU_INVARIANT を書かずに if (hp < 0) { hp = 0; } を update の末尾に足すだけでは、何が違うと思うか。

答え

clamp は「症状を隠す」、invariant は「症状に気づかせる」。hp = 0; で clamp すると画面上は正しく見えるが、なぜ 3 回被弾しただけで瀕死になったのか (1 回あたりのダメージが大きすぎる、無敵時間がない、等) という設計上の問題は隠れたまま残る。MITIRU_INVARIANT は「そもそも負になる経路がある」ことを毎フレーム教え続けるので、直す動機が消えない。両方を組み合わせる (invariant で気づく → 根本原因を直す、clamp は最後の安全網として残してもよい) のが実務的。

05

録画と巻き戻し

この章のゴールいま動かしたプレイを録画して、あとから寸分違わず再生する。過去のフレームへ巻き戻して見る。

この章の主役は C++ のコードではなく mitiru_host と mitiru コマンド。コードは第2章の「動く四角」に 2 行足すだけで、あとは全部コマンドで体験する。

1状態を毎フレーム覚えさせる

決定論docs/GLOSSARY.md

同じ入力を渡せば、何回実行しても同じ結果になること。乱数や実時刻を直接使わず、dt の積み上げだけで状態が決まっているコードは決定論的。

なぜ

MitiruEngine は状態をぜんぶ 1 個の flat POD (GameMemory) にまとめる設計にしている。だから host は毎フレームその bytes をまるごとコピーして覚えておける。MITIRU_REWIND_BUFFER はその「覚えておく」機能を有効にするだけの 1 行。

操作

第2章のコードに、勝手にはねるボールと 2 行を足す。入力に頼らず毎フレーム状態が変わるので、巻き戻しの効果が画面で分かりやすい。

src/main.cpp#include の下に追加
#include <mitiru/module/AutoReflect.hpp>
src/main.cppstruct MyGame の中、x, y の下に追加
    float ballX = 200.0f, ballY = 200.0f;
    float ballVX = 220.0f, ballVY = 180.0f;
src/main.cppupdate の末尾に追加
        ballX += ballVX * dt;
        ballY += ballVY * dt;
        if (ballX < 20.0f || ballX > 1260.0f) { ballVX = -ballVX; }
        if (ballY < 20.0f || ballY > 700.0f) { ballVY = -ballVY; }
src/main.cppdraw の中、四角を描く行の上に追加
        s.drawCircleFrame({ballX, ballY}, 18.0f, hex(0xF5C842), 4.0f);
src/main.cppMITIRU_GAME(MyGame) の上下に追加
MITIRU_REFLECT_AUTO(MyGame);   // MyGame の前 (struct 定義の後ろ)

MITIRU_GAME(MyGame)
MITIRU_REWIND_BUFFER(600);     // MITIRU_GAME の下。600 フレーム = 60fps で 10 秒ぶん

読み方

MITIRU_REFLECT_AUTO(MyGame)
inspector が「どのフィールドがどう変わったか」を名前つきで見せられるようにする (無くても巻き戻し自体は動く)
MITIRU_REWIND_BUFFER(600)
直近 600 フレームぶんの GameMemory を host がリングバッファに積む。数値は容量とのトレードオフ (増やすほどメモリを使う)
確認

mitiru run すると、青い四角 (入力で動く) と金色の輪 (勝手にはねるボール) が見える。

2録画して、寸分違わず再生する

なぜ

入力列 (キー・マウスの生値) だけを保存しておけば、決定論的なゲームは「同じ計算をもう一度させる」だけで元と同じ結果になる。動画ではなく入力を録っているので、ファイルはとても小さい。

操作

ターミナルで、ビルド済みの mitiru_host.exe と DLL に対して直接コマンドを打つ (Windows のみ、パスは自分の環境の物に置き換える)。

  1. mitiru_host.exe my_game.dll --record demo.mtrr で実際にプレイしながら録画する
  2. ウィンドウを閉じると demo.mtrr ができる
  3. mitiru_host.exe my_game.dll --replay-test demo.mtrr --json で寸分違わず再生し、結果を機械可読な 1 行 JSON で見る
確認

ターミナルに {"framesCompared":...,"reason":"bit_exact","verdict":"PASS"} のような行が出る。verdict が PASS なら、記録したフレーム数ぶん、GameMemory が 1 byte も違わず再現できたということ。

3別窓で過去へ戻る

なぜ

rewind inspector は「今の GameMemory を過去のバイト列で丸ごと上書きする」だけの単純な仕組み。物理エンジンの途中経過も含めて戻せるのは、状態がぜんぶ 1 個の struct にまとまっているから (第4章までで作った物もそのまま対象になる)。

操作
  1. mitiru run --inspect rewind と打つ (または mitiru run --learn でも同じ窓が開く)
  2. ゲーム画面の隣に、時間を戻すバーを持つ別窓が開く
  3. プレイしたあと、バーを左へ動かす
確認

バーを動かすと、ボールの位置や自分の四角の位置が過去の状態に戻る。バーを離せば、そこから続きが始まる。

42本の録画を比べる

なぜ

「直したつもりが同じ入力で違う結果になっていないか」を確かめたいことがある (リファクタ後の回帰確認等)。mitiru replay --diff は 2 つの .mtrr の GameMemory を frame 単位で比べ、最初に食い違ったフレームを教えてくれる。

操作

プロジェクトのフォルダで打つ (mitiru.toml があるフォルダ)。

ターミナル
mitiru replay --diff demo.mtrr demo.mtrr
確認

同じファイル同士を比べると「一致 ── N frame とも GameMemory が byte-exact」のように出る。実際に使うときは、修正前後で録り直した 2 本を渡す。

録画が一致しないとき: 乱数や実時刻 (std::chrono::system_clock 等) を update の中で直接使っていないか疑う。決定論を保つには「入力と dt だけで次の状態が決まる」形を保つ。
改造課題・5分

ボールの初速をコード上で変えて (ballVX = 400.0f; 等)、録画をもう一度取り直し、変更前の録画と mitiru replay --diff で比べる。

ヒント

入力列は同じでも、コード自体が変わればボールの軌道は最初のフレームから違ってくるはず。divergedAtFrame のような値が早い段階で出れば期待どおり。

質問

--replay-test は「入力を再生し直して同じ結果になるか」を確かめるものだった。では「録画された画面 (動画) をそのまま流す」のと何が違うと思うか。

答え

録画されているのは入力であって画面ではない。だからファイルは小さく、コードを直した後の挙動も同じ入力で確かめ直せる (動画では「直した後にどう動いたか」は分からない)。一方、決定論が崩れている (乱数・実時刻・未初期化メモリ等) と、同じ入力を渡しても違う結果になり --replay-test は FAIL になる。

06

分岐エディタ

この章のゴールゲーム画面の上に出たプレイヤーの枠をドラッグして位置を試し、残すか捨てるか選ぶ。

docs/BRANCH_EDITOR.md (ADR 0035) が定義する「分岐エディタ」を、第2章の「動く四角」で体験する。Unity/Godot の Inspector ドラッグと違い、触った結果は試してから残すか捨てるか選ぶ ── 触った瞬間に本番へは書き込まない。

1描画コマンドに「どのフィールドか」の名札をつける

Canvasdocs/GLOSSARY.md

Screen と同じ絵を描く道具だが、描画を「後で host が読める POD コマンド列」として積む。beginObject/endObject は Canvas だけが持つ。

なぜ

分岐エディタの scene_view は、画面のどこに何が描かれているかを座標だけでは知らない。beginObject(名前, x のフィールド名, y のフィールド名) で「この区間の描画は x/y というフィールドの絵です」と教えると、host が画面上に枠を出し、ドラッグ結果をその名前のフィールドへ書き戻せるようになる。

操作

第2章のコードの draw を Screen& ではなく Canvas& を受け取る形に書き換え、四角を描く前後に beginObject/endObject を挟む。

src/main.cpp#include の下に追加
#include <mitiru/module/AutoReflect.hpp>
src/main.cppdraw を置き換え (Screen& ではなく Canvas& を受け取る)
    void draw(Canvas& c) const
    {
        c.fillScreen(hex(0x101018));

        c.beginObject("player", "x", "y");
        c.drawRectCentered(x, y, 40.0f, 40.0f, hex(0x4C95F2));
        c.endObject();
    }
src/main.cppMITIRU_GAME の上に追加
MITIRU_REFLECT_AUTO(MyGame);

読み方

beginObject("player", "x", "y")
以後 endObject() までのコマンドに「player という物の x/y フィールド」という名札を乗せる。x/y は Vec2 のようなまとまりではなく別々の scalar なので、明示 3 引数版を使う
MITIRU_REFLECT_AUTO(MyGame)
ドラッグ結果を「x というフィールドはメモリのここ」と引けるようにする。これが無いと枠は出せても書き戻せない
確認

mitiru run は今までどおり四角が動く見た目のまま (見た目は変わらない、名札は host 側だけが読む)。

2シーンビューでドラッグする

操作
  1. mitiru run --inspect scene_view と打つ
  2. ゲーム画面と同じ絵が映った別窓が開き、プレイヤーの四角に枠が出る
  3. 枠をドラッグして、四角の位置を試しに動かす
なぜ

ドラッグは PUT /api/ai/state で「今の値を複製して書き換え、結果を見せて、すぐ元へ戻す」形になっている。この時点ではまだ何も確定していない ── これがメガエディタ (触った瞬間に本番へ書く) との違い。

確認

ドラッグ中はプレイヤーが追随して見える。指を離すと、しばらくして元の位置に戻る (試しただけなので)。

3残すか、捨てるか選ぶ

残す/捨てるdocs/BRANCH_EDITOR.md

「残す」は今 live で動いているゲームの状態へ本当に書き込む (POST /api/ai/commit)。「捨てる」は何もしない (POST /api/ai/discard)、ドラッグ前の状態のまま続く。

なぜ

「試してから選ぶ」の 1 拍が、メガエディタ (触った瞬間に確定) と分岐エディタの一番の違い。数値をいくつか候補として並べて選ぶ「候補ゴースト」も同じ仕組みの応用 (docs/BRANCH_EDITOR.md の「分岐候補」節)。

操作

scene_view のミニ inspector に出るボタンで、気に入った位置なら「残す」、気に入らなければ「捨てる」を選ぶ。

確認

「残す」を選ぶとその位置がそのままゲームの本当の状態になる (次のフレームからもそこにいる)。「捨てる」を選ぶとドラッグ前の位置に戻る。

この章でやらないこと: 分岐エディタは「触った結果を試してから選ぶ」道具であって、Hierarchy パネルや Prefab のような全機能エディタではない (CLAUDE.md の「メガエディタ系の提案は禁止」)。ノードベースのビジュアルスクリプトの類もここには足さない。
改造課題・5分

もう 1 個、動かないゴール地点の四角を足し、それにも beginObject で名札をつける。フィールド名は goalX/goalY のように分ける。

ヒント

struct MyGame に float goalX = 980.0f, goalY = 200.0f; を足し、draw の中で beginObject("goal", "goalX", "goalY") → 描画 → endObject() を、player とは別に挟む。

質問

分岐エディタのドラッグは、なぜ第5章の巻き戻し (rewind) と同じ「1個の flat な GameMemory」という設計の上に成り立っていると思うか。

答え

「今の状態を複製して書き換え、比べて、選ぶ」という操作が、状態が 1 個の連続したバイト列だからこそ単純な複製・書き戻しで実現できる。状態がクラスの階層やヒープのあちこちに散らばっていたら、「複製」ひとつとっても何をどこまで複製すればよいか自明ではなくなる。GameMemory が flat POD であるという第2章からの前提が、巻き戻し・録画・分岐エディタの 3 つ全部を同じ仕組みの上で動かしている。

この先の章

ここまでで、状態を 1 個の struct にまとめる考え方 (flat POD) が、巻き戻し・録画・分岐エディタという MitiruEngine 独自の機能をどれも支えていることを一通り触った。この先はカリキュラム (docs/EXAMPLE_STANDARD.md) の各章や、興味に応じて次のドキュメントへ進むとよい。

07+セーブ・ロードとリスタート（examples/restart_save）次

先に読みたい場合は docs/GOLDEN_PATH.md（一本道の全体像）と examples/README.md（章ごとのサンプル集）を見るとよい。

Aa

用語集

ここに出てきた言葉のうち、この教本だけで使うものをまとめた。エンジン全体の用語は docs/GLOSSARY.md を見る。

dtデルタタイム

update に毎フレーム渡される、前フレームからの経過秒。速さに dt を掛けると、フレームレートが変わっても動きの速さが変わらない。

Stick

in.move() が返す {x, y} の組。-1..1 の範囲で、矢印キー・WASD・パッドのスティックをまとめて表す。

Screen

draw に渡される、絵を描くための道具。fillScreen / drawRectCentered / drawCircleFrame / drawTextInRect などを持つ。

hex(0xRRGGBB)

16 進数で色を作る関数。0x4C95F2 のように書くと、赤・緑・青の順で 2 桁ずつ。
