AI 連携

AI エージェントと作る

MitiruEngine は、Claude Code や Codex などの AI エージェントとゲームを作ることを、正面から支援します。実行中のゲームの画面・状態・音を HTTP で構造化 JSON として読め、修正が正しいかを mitiru verify が機械的に判定します。これらは後付けのプラグインではなく、状態を 1 個の flat POD にまとめる設計から生えたネイティブの仕組みです。AI が「書く → 観る → 直す → 検証する」を、人間の目を借りずに一周できます。

後付けではなく、ネイティブの仕組み

多くのエンジンでは、AI に状態を見せるには専用の出力コードを書き足す必要があります。MitiruEngine では、ゲームの全状態がもともと 1 個の struct（flat POD）にまとまっていて、それをエンジンが預かっています。だから、AI が読む・遡る・別の入力で試す、という仕組みが同じ 1 つの状態から出てきます。AI 側の「見える範囲」を、ゲームコードを汚さずに広げられるのが要点です。

  • 状態を読む ── 全フィールドを構造化 JSON で。フレーム間の差分も。
  • 画面を意味で読む ── ピクセルではなく「何をどこに描いたか」の draw list で。
  • 過去へ遡る・別世界で試す ── 記録した状態へ巻き戻し、別の入力で再実行。
  • 修正を機械判定する ── mitiru verify が build → 起動 → 観測 → 判定までを 1 コマンドで。

ループの形 — 観る・突き合わせる・検証する

従来は「AI がコードを書き、人間が実行結果を見て指摘する」形でした。このエンジンでは、結果の観測と判定も機械側に渡せます。

コードを直す  -->  mitiru verify        # build + 起動 + 判定が 1 コマンド
画面を観る    -->  GET /api/ai/frame    # draw list ("HP 79" がどの矩形か)
状態を読む    -->  GET /api/ai/state    # 全フィールドの構造化 JSON
原因を絞る    -->  GET /api/ai/diff     # フレーム間で何が変わったか
正しさを示す  -->  mitiru verify --replay  # bit-exact 再現で機械判定

有効化 — 環境変数 1 個

環境変数 MITIRU_AI=1 を立てて起動するだけです。ゲーム側のコード変更は要りません。host が 127.0.0.1:8090（変更は MITIRU_AI_PORT）で HTTP API を開きます。ローカル限定で、普段の起動では開きません。

set MITIRU_AI=1
mitiru run
# stderr に → [ai] HTTP API listening on 127.0.0.1:8090

画面を「意味」で読む — /api/ai/frame

スクリーンショットの画素から座標を推測する必要はありません。/api/ai/frame は、そのフレームにどの描画 API が・どの矩形に・何を描いたかを返します。テキスト描画は内容ごと載ります。以下はサンプルゲームの実測そのままです。

{"frameNumber":8652,"screen":{"width":1280,"height":720},
 "drawCalls":[
   {"call":"drawRect",  "x":24, "y":24, "w":360,   "h":22},
   {"call":"drawRect",  "x":24, "y":24, "w":284.4, "h":22},
   {"call":"drawText",  "x":398,"y":22, "w":110,   "h":22, "text":"HP 79"},
   {"call":"drawCircle","x":618,"y":338,"w":44,    "h":44},
   ...
 ],
 "screenshot":{"width":640,"height":360,"pngBase64":"..."}}

HP バーの外枠が幅 360、中身が 284.4 ── つまり残り 79% だと、画像処理なしで読めます。縮小 PNG も同じレスポンスに入ります（?screenshot=0 で省略可）。PNG には HTML / CSS の HUD も合成済みで、プレイヤーが見ている画面そのものが渡ります。

初回の呼び出しで記録が始まります（エントリは次フレームから）。音も同様に /api/ai/audio で「どの SE / BGM が・いつ・どの音量と pitch で鳴ったか」を構造化で読めます。

状態を読む — state / diff / branch

ゲームの全状態は 1 個の flat POD（GameMemory）にあります。MITIRU_REFLECT でフィールドを申告すると、host が現フレームの状態を丸ごと JSON 化して返します。

GET /api/ai/state            # {"hearts":3,"pos_x":32.0,"scene":0,...} 全フィールド
GET /api/ai/diff?from=0&to=60 # 60 フレームで変わった値だけ
POST /api/ai/branch          # この状態から「←を 30 フレーム押したら?」を別世界で実行

「画面では HP バーが 79% なのに state の hp は 83」── そういう見た目と内部のズレが、frame と state の突き合わせで一発で見つかります。

検証する — mitiru verify

「直した、たぶん動く」を禁止できます。mitiru verify は build → 起動 → 観測 → 判定までを 1 コマンドで実行し、結果を JSON 1 個と exit code で返します。CI にそのまま置けます。

mitiru verify                       # build + 起動 + screenshot 取得
mitiru verify --golden ref.png      # 基準画像と画素比較
mitiru verify --replay play.mtrr    # 録画した操作を bit-exact 再現できるか

# → {"build":"ok","verdict":"pass",...}   exit 0=pass / 1=fail / 2=build error

リプレイ検証は決定論（同じ入力 → 同じ結果）の上に立っているので、「修正前に録った操作が修正後も同じ結果になるか」をバイト単位で判定します。視覚は golden 画像、ロジックはリプレイ、と二方向から機械検証できます。

Claude Code から使う — mitiru mcp

mitiru mcp が上の API 群を MCP（Model Context Protocol）のツールとして公開します。設定はプロジェクトの .mcp.json に 1 行です。

{"mcpServers": {"mitiru": {"command": "mitiru", "args": ["mcp"]}}}

これで AI エージェントの手元に game_state / frame / screenshot / simulate_input（入力注入）/ pause / step（コマ送り）/ verify などのツールが生えます。エージェントは自分でゲームを動かし、コマ送りで観察し、判定まで取れます。

API 一覧 — 全エンドポイント

host が開く HTTP API の全量です。AI のループで普段使うのは上の 2 グループで、下の 2 グループはブラウザの操作盤（control panel）やツール窓が使っている口です ── 同じサーバーに同居しているので、必要なら直接叩けます。

観測 — 画面・状態・音を読む

GET /api/ai/framedraw list（描画 API・矩形・テキスト内容）+ 縮小 PNG。初回呼び出しで記録開始
GET /api/ai/stateGameMemory 全フィールドの構造化 JSON
GET /api/ai/diff?from=&to=2 フレーム間の状態差分
GET /api/ai/audio?max=N最近の音イベント（SE / BGM の再生・停止・音量・pitch）
GET /api/ai/ringsize状態リングの記録フレーム数（どこまで遡れるか）
POST /api/ai/branch反実仮想 — この状態から別入力で N フレーム実行
GET /api/screenshot画面 PNG（HTML HUD 合成済み、width / height でリサイズ）
GET /api/health生存確認（frame 番号と経過時間）

実行制御 — 動かす・止める・巻き戻す

POST /api/input/simulate入力注入 — 外からゲームを操作する
POST /api/runtime/pauseポーズをトグル
POST /api/runtime/step1 フレームだけ進める（コマ送り）
POST /api/runtime/timescale倍速・スロー（{"value":0.25}）
POST /api/runtime/resimk フレーム巻き戻し、記録済み入力で再生（{"frames":120}）。ホットリロード後なら「同じ入力・新しいコード」でバグの瞬間を再現できる
POST /api/runtime/lofilofi ポスト FX（低解像度・減色）をトグル
POST /api/runtime/quitゲームを終了
GET /api/runtime/statuspaused / timeScale / frame の現在値

GET /api/observe/inspect/at?back=NN 個前の過去スナップショット
GET /api/observe/inspect/depthスナップショット履歴の深さと容量
GET /api/scene · /api/scene/treeシーン全体 / シーンツリー

操作盤・シーン編集 — control panel が使う口

GET /consoleブラウザの control panel（HTML。/ でも開く）
GET /api/commands[/カテゴリ]実行できるコマンドの一覧

詳細な手順とつまずきやすい点は、リポジトリの docs/AI_WORKFLOW.md にあります。

なぜできるか — flat POD と決定論の果実

この一式は後付けのプラグインではなく、設計の帰結として生えています。

  • 状態が 1 個の flat POD だから、全状態の JSON 化・フレーム間 diff・過去への巻き戻し・別世界での再実行（branch）・記録入力での再シミュレーション（/api/runtime/resim）が、同じ 1 つのメモリ領域に対する操作として実装できます。状態が数千のオブジェクトに散っているエンジンでは、この「全状態を読む」が原理的に作れません。
  • 実行が決定論的 だから、「同じ入力なら同じ結果」を前提に、リプレイがそのまま回帰テストになります。AI の修正が何かを壊していないかを、人間の目視ではなくバイト比較で判定できます。
  • HUD が HTML / CSS だから、スクリーンショットには UI まで含めた「プレイヤーが見る画面」がそのまま写ります。

土台の考え方は、機能リファレンス の巻き戻し・リプレイの章と、リポジトリの docs/FLAT_POD.md に詳しくあります。
