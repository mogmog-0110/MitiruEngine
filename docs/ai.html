AI 連携

AI エージェントと作る

MitiruEngine は、Claude Code や Codex などの AI エージェントとゲームを作ることを、正面から支えます。実行中のゲームの画面・状態・音を、HTTP から読みやすい JSON で受け取れて、修正が正しいかを mitiru verify が機械的に判定します。これらは後付けの追加機能ではなく、ゲームの状態をまるごとコピーできる 1 個のかたまりに置く設計から自然に出てくるものです。AI が「書く・観る・直す・確かめる」を、人の目を借りずに一周できます。

できること

多くのエンジンでは、AI にゲームの状態を見せるのに、専用の書き出しコードを足す必要があります。MitiruEngine では、ゲームの状態がもともと 1 個のかたまりにまとまっていて、それをエンジンが預かっています。だから、AI が読む・巻き戻す・別の入力で試す、といった仕組みが同じ 1 つの状態から出てきます。ゲームのコードを汚さずに、AI に見える範囲を広げられるのが要点です。

  • 状態を読む ── すべての値を JSON で。フレーム間で変わった分だけも取れます。
  • 画面を読む ── 画素ではなく「何を・どこに描いたか」の一覧で。
  • 巻き戻して試す ── 記録した状態へ戻し、別の入力でやり直す。
  • 修正したものを判定する ── mitiru verify が、ビルド・起動・観測・判定を 1 コマンドで。

開発の流れ

これまでは「AI がコードを書き、人間が実行結果を見て指摘する」形でした。このエンジンでは、結果を観ることと正しさの判定も、機械側に渡せます。

コードを直す  -->  mitiru verify        # ビルド + 起動 + 判定が 1 コマンド
画面を観る    -->  GET /api/ai/frame    # 何をどこに描いたか（"HP 79" がどの矩形か）
状態を読む    -->  GET /api/ai/state    # すべての値の JSON
原因を絞る    -->  GET /api/ai/diff     # フレーム間で変わった値だけ
正しさを示す  -->  mitiru verify --replay  # 録画を 1 bit も違わず再現して判定

有効化

環境変数 MITIRU_AI=1 を立てて起動するだけです。ゲーム側のコード変更は要りません。host が 127.0.0.1:8090（変更は MITIRU_AI_PORT）で HTTP の口を開きます。手元のパソコンの中だけで、普段の起動では開きません。

set MITIRU_AI=1
mitiru run
# stderr に → [ai] HTTP API listening on 127.0.0.1:8090

画面を読む

スクリーンショットの画素から座標を推測する必要はありません。/api/ai/frame は、そのフレームに何が・どの位置に・どう描かれたかを返します。文字は内容ごと載ります。以下はサンプルゲームの実測そのままです。

{"frameNumber":8652,"screen":{"width":1280,"height":720},
 "drawCalls":[
   {"call":"drawRect",  "x":24, "y":24, "w":360,   "h":22},
   {"call":"drawRect",  "x":24, "y":24, "w":284.4, "h":22},
   {"call":"drawText",  "x":398,"y":22, "w":110,   "h":22, "text":"HP 79"},
   {"call":"drawCircle","x":618,"y":338,"w":44,    "h":44},
   ...
 ],
 "screenshot":{"width":640,"height":360,"pngBase64":"..."}}

HP バーの外枠が幅 360、中身が 284.4 ── つまり残り 79% だと、画像処理なしで読めます。縮小した PNG も同じ返事に入ります（?screenshot=0 で省略可）。PNG には HTML / CSS の HUD も合成済みで、プレイヤーが見ている画面そのものが渡ります。

初回の呼び出しで記録が始まります（中身は次のフレームから）。音も同じように /api/ai/audio で「どの効果音 / BGM が・いつ・どの音量と高さで鳴ったか」を読めます。

状態を読む

ゲームの全状態は、まるごとコピーできる 1 個のかたまりにあります。MITIRU_REFLECT でどのフィールドを見せるか申告すると、いまのフレームの状態がまるごと JSON で返ります。

GET /api/ai/state            # {"hearts":3,"pos_x":32.0,"scene":0,...} すべての値
GET /api/ai/diff?from=0&to=60 # 60 フレームで変わった値だけ
POST /api/ai/branch          # この状態から「←を 30 フレーム押したら?」を別に試す

「画面では HP バーが 79% なのに、状態の hp は 83」── そういう見た目と中身のズレが、画面と状態を突き合わせると一発で見つかります。

検証する

「なおした、たぶん動く」を禁止できます。mitiru verify は、ビルド・起動・観測・判定までを 1 コマンドで実行し、結果を JSON 1 個と終了コードで返します。CI にそのまま置けます。

mitiru verify                       # ビルド + 起動 + スクショ取得
mitiru verify --golden ref.png      # 基準の画像と見比べる
mitiru verify --replay play.mtrr    # 録画した操作を 1 bit も違わず再現できるか

# → {"build":"ok","verdict":"pass",...}   終了コード 0=pass / 1=fail / 2=build error

リプレイでの検証は「同じ入力なら同じ結果になる」ことの上に立っているので、「なおす前に録った操作が、修正後も同じ結果になるか」をバイト単位で判定します。見た目は基準の画像との比較、中身はリプレイ、と二方向から機械で確かめられます。

Claude Code から使う

mitiru mcp が、上の API 群を MCP（Model Context Protocol）のツールとして公開します。設定はプロジェクトの .mcp.json に 1 行です。

{"mcpServers": {"mitiru": {"command": "mitiru", "args": ["mcp"]}}}

これで AI エージェントの手元に game_state / frame / screenshot / simulate_input（入力の注入）/ pause / step（コマ送り）/ verify などのツールが生えます。エージェントは自分でゲームを動かし、コマ送りで観察し、判定まで取れます。

API 一覧

host が開く HTTP の口の全量です。AI のループで普段使うのは上の 2 グループで、下の 2 グループはブラウザの操作盤やツール窓が使っている口です ── 同じサーバーに同居しているので、必要なら直接叩けます。

観測 — 画面・状態・音を読む

GET /api/ai/frame何をどこに描いたかの一覧（描画の種類・位置・文字の内容）＋ 縮小 PNG。初回呼び出しで記録開始
GET /api/ai/stateゲームの全状態（すべてのフィールド）の構造化 JSON
GET /api/ai/diff?from=&to=2 フレーム間の状態の差分
GET /api/ai/audio?max=N最近の音イベント（効果音 / BGM の再生・停止・音量・高さ）
GET /api/ai/ringsize記録してあるフレーム数（どこまで遡れるか）
POST /api/ai/branchこの状態から別の入力で N フレーム実行して、結果を試す
GET /api/screenshot画面 PNG（HTML の HUD 合成済み、width / height でリサイズ）
GET /api/health生存確認（フレーム番号と経過時間）

実行制御 — 動かす・止める・巻き戻す

POST /api/input/simulate入力の注入 ── 外からゲームを操作する
POST /api/runtime/pauseポーズを切り替える
POST /api/runtime/step1 フレームだけ進める（コマ送り）
POST /api/runtime/timescale倍速・スロー（{"value":0.25}）
POST /api/runtime/resimk フレーム巻き戻して、記録した入力で再生（{"frames":120}）。コードを修正したあとなら「同じ入力・新しいコード」でバグの瞬間を再現できる
POST /api/runtime/lofi低解像度・減色の演出を切り替える
POST /api/runtime/quitゲームを終了
GET /api/runtime/statusポーズ中か / 速度 / フレームの現在値

検査 — ツール窓と同じのぞき窓

GET /api/observe/schema観測データの形（JSON Schema）
GET /api/observe/inspect?prefix=観察窓の値の一覧（prefix で絞り込み）
GET /api/observe/inspect/at?back=NN 個前の過去のスナップショット
GET /api/observe/inspect/depth記録している履歴の深さと容量
GET /api/scene · /api/scene/treeシーン全体 / シーンツリー
GET /api/render/stats描画の統計
GET /api/debug/log · /api/debug/errors直近のログ / エラー一覧
GET /api/status · /api/configエンジンの状態 / 設定
GET /api/project/infoプロジェクト情報
GET /api/flags · POST /api/flagデバッグ用スイッチの一覧 / 変更

操作盤・シーン編集 — ブラウザの操作盤が使う口

GET /consoleブラウザの操作盤（HTML。/ でも開く）
GET /api/commands[/カテゴリ]実行できるコマンドの一覧
POST /api/commandコマンドを 1 つ実行
POST /api/game/run · /api/game/stopゲームの起動 / 停止
POST /api/scene/create-node · save · loadノード作成 / シーン保存・読込
PUT · DELETE /api/scene/node/<id>ノードの更新 / 削除（…/trait で trait の追加 / 削除）
GET /api/editor/state ほか editor 系エディタ視点・選択（camera / select / focus / screenshot）

詳しい手順とつまずきやすい点は、リポジトリの docs/AI_WORKFLOW.md にあります。

なぜできるか

この一式は後付けの追加機能ではなく、設計の帰結として生えています。

  • 状態がまるごとコピーできる 1 個のかたまりだから、全状態を JSON にする・フレーム間の差分を取る・過去へ巻き戻す・別の入力で試す・記録した入力で再生する、が、すべて同じひとかたまりへの操作として作れます。状態が数千のオブジェクトに散らばっているエンジンでは、この「全状態をまるごと読む」が原理的に作れません。
  • 同じ入力なら同じ結果になるから、リプレイがそのまま回帰テストになります。AI の修正が何かを壊していないかを、目視ではなくバイト比較で判定できます。
  • HUD が HTML / CSS だから、スクリーンショットには UI まで含めた「プレイヤーが見る画面」がそのまま写ります。

土台の考え方は、機能リファレンス の巻き戻し・リプレイの節に詳しくあります。
