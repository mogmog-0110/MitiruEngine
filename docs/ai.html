Observability / AI

AI と作る — 観測と検証

実行中のゲームの画面・状態・音を、HTTP で外から構造化 JSON として読める。画面はピクセルではなく「何をどこに描いたか」の draw list で渡り、修正の正しさは mitiru verify が機械的に判定する。AI エージェントが「書く → 観る → 直す → 検証する」を人間の目を借りずに一周できる。もちろん人間や CI から使ってもいい。

ループの形 — 観る・突き合わせる・検証する

従来は「AI がコードを書き、人間が実行結果を見て指摘する」だった。このエンジンでは結果の観測と判定も機械側に渡せる。

コードを直す  -->  mitiru verify        # build + 起動 + 判定が 1 コマンド
画面を観る    -->  GET /api/ai/frame    # draw list ("HP 79" がどの矩形か)
状態を読む    -->  GET /api/ai/state    # 全フィールドの構造化 JSON
原因を絞る    -->  GET /api/ai/diff     # フレーム間で何が変わったか
正しさを示す  -->  mitiru verify --replay  # bit-exact 再現で機械判定

有効化 — 環境変数 1 個

環境変数 MITIRU_AI=1 を立てて起動するだけ。ゲーム側のコード変更は要らない。host が 127.0.0.1:8090（変更は MITIRU_AI_PORT）で HTTP API を開く。ローカル限定で、普段の起動では一切開かない。

set MITIRU_AI=1
mitiru run
# stderr に → [ai] HTTP API listening on 127.0.0.1:8090

画面を「意味」で読む — /api/ai/frame

スクリーンショットの画素から座標を推測する必要はない。/api/ai/frame は、そのフレームにどの描画 API が・どの矩形に・何を描いたかを返す。テキスト描画は内容ごと載る。以下はサンプルゲームの実測そのまま。

{"frameNumber":8652,"screen":{"width":1280,"height":720},
 "drawCalls":[
   {"call":"drawRect",  "x":24, "y":24, "w":360,   "h":22},
   {"call":"drawRect",  "x":24, "y":24, "w":284.4, "h":22},
   {"call":"drawText",  "x":398,"y":22, "w":110,   "h":22, "text":"HP 79"},
   {"call":"drawCircle","x":618,"y":338,"w":44,    "h":44},
   ...
 ],
 "screenshot":{"width":640,"height":360,"pngBase64":"..."}}

HP バーの外枠が幅 360、中身が 284.4 — つまり 残り 79% だと、画像処理なしで読める。縮小 PNG も同じレスポンスに入る（?screenshot=0 で省略可）。PNG には HTML / CSS の HUD も合成済みで、プレイヤーが見ている画面そのものが渡る。

初回の呼び出しで記録が始まる（エントリは次フレームから）。音も同様に /api/ai/audio で「どの SE / BGM が・いつ・どの音量と pitch で鳴ったか」を構造化で読める。

状態を読む — state / diff / branch

ゲームの全状態は 1 個の flat POD（GameMemory）にある。MITIRU_REFLECT でフィールドを申告すると、host が現フレームの状態を丸ごと JSON 化して返す。

GET /api/ai/state            # {"hearts":3,"pos_x":32.0,"scene":0,...} 全フィールド
GET /api/ai/diff?from=0&to=60 # 60 フレームで変わった値だけ
POST /api/ai/branch          # この状態から「←を 30 フレーム押したら?」を別世界で実行

「画面では HP バーが 79% なのに state の hp は 83」── そういう見た目と内部のズレが、frame と state の突き合わせで一発で見つかる。

検証する — mitiru verify

「直した、たぶん動く」を禁止できる。mitiru verify は build → 起動 → 観測 → 判定までを 1 コマンドで実行し、結果を JSON 1 個と exit code で返す。CI にそのまま置ける。

mitiru verify                       # build + 起動 + screenshot 取得
mitiru verify --golden ref.png      # 基準画像と画素比較
mitiru verify --replay play.mtrr    # 録画した操作を bit-exact 再現できるか

# → {"build":"ok","verdict":"pass",...}   exit 0=pass / 1=fail / 2=build error

リプレイ検証は決定論（同じ入力 → 同じ結果）の上に立っているので、「修正前に録った操作が修正後も同じ結果になるか」をバイト単位で判定する。視覚は golden 画像、ロジックはリプレイ、と二方向から機械検証できる。

Claude Code から使う — mitiru mcp

mitiru mcp が上の API 群を MCP（Model Context Protocol）のツールとして公開する。設定はプロジェクトの .mcp.json に 1 行。

{"mcpServers": {"mitiru": {"command": "mitiru", "args": ["mcp"]}}}

これで AI エージェントの手元に game_state / frame / screenshot / simulate_input（入力注入）/ pause / step（コマ送り）/ verify などのツールが生える。エージェントは自分でゲームを動かし、コマ送りで観察し、判定まで取る。

API 一覧

GET /api/ai/framedraw list（描画 API・矩形・テキスト内容）+ 縮小 PNG
GET /api/ai/stateGameMemory 全フィールドの構造化 JSON
GET /api/ai/diff2 フレーム間の状態差分
POST /api/ai/branch反実仮想 — この状態から別入力で N フレーム実行
GET /api/ai/audio最近の音イベント（SE / BGM の再生・停止・音量・pitch）
GET /api/screenshot画面 PNG（HTML HUD 合成済み、width/height でリサイズ）
POST /api/input/simulate入力注入 — 外からゲームを操作する
POST /api/runtime/pause · step · timescaleポーズ・コマ送り・倍速
GET /api/scene/tree · /api/healthシーンツリー / 生存確認

詳細な手順とつまずきやすい点はリポジトリの docs/AI_WORKFLOW.md にある。

なぜできるか — flat POD と決定論の果実

この一式は後付けのプラグインではなく、設計の帰結として生えている。

  • 状態が 1 個の flat POD だから、全状態の JSON 化・フレーム間 diff・過去への巻き戻し・別世界での再実行（branch）が、同じ 1 つのメモリ領域に対する操作として実装できる。状態が数千のオブジェクトに散っているエンジンでは、この「全状態を読む」が原理的に作れない。
  • 実行が決定論的 だから、「同じ入力なら同じ結果」を前提に、リプレイがそのまま回帰テストになる。AI の修正が何かを壊していないかを、人間の目視ではなくバイト比較で判定できる。
  • HUD が HTML / CSS だから、スクリーンショットには UI まで含めた「プレイヤーが見る画面」がそのまま写る。

土台の考え方は 機能リファレンス の巻き戻し・リプレイの章と、リポジトリの docs/FLAT_POD.md に詳しい。
